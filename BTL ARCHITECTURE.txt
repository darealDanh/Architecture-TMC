1. System Context and Requirements


TMC needs a QR code-based system to control employee access at its factories and to produce monthly attendance data for payroll. This section describes the context of that system, its objectives and scope, and the functional and non-functional requirements we use as the basis for the architecture in the following sections.


1.1. System Context


1.1.1. Business Context


TMC Manufacturing Joint Stock Company operates in the manufacturing sector and owns two factories: Binh Duong, with approximately 800 employees, and Long An, with approximately 600 employees. The company needs a single system that serves two purposes: it must control employee access to the workplace, and it must produce accurate monthly attendance data for payroll.


Employees are identified by a personal QR code, displayed on their own smartphones through the company's mobile application, web portal or email system. Each factory has access gates equipped with a QR scanner and a turnstile. When an employee presents a QR code at a gate, the TMC system validates the code and requests the existing Turnstile Control System to unlock the gate. The access event, either an entry or an exit, is then recorded as an attendance transaction.


At the end of each month, the attendance data is transmitted to the company's existing HR/Payroll System through its API. The data must be available for reconciliation before 12:00 PM on the first day of the following month. Payroll processing itself remains the responsibility of the HR/Payroll System.


Based on the description, we identify the following architectural drivers. The heaviest load comes at shift changes, when each factory handles around 800 access transactions within 30 minutes while employees queue at the gates. The two factories are in different locations, so gates run at two sites while reports cover the whole company. Gate control and payroll already have their own systems, which TMC has to work with rather than replace. Finally, the system holds personal data about employees and their movements, so it falls under data privacy regulations.

3. Architecture Style
Before analyzing the specific architecture styles, it is crucial to establish a common deployment baseline for the edge devices. Requirements FR-AT-06 and NFR-06 require every gate station to validate QR codes and store access events locally, whichever style is chosen for the central system. Offline operation is therefore handled by the gate stations in all candidates, and the analysis below compares the styles for the central system.
3.1 Layered Architecture
3.1.1 Core concept
Layered Architecture is a pattern that organizes system components horizontally into logical layers. Each layer has a specific role and separation of concerns. The core principle is that the request flow goes top-down, where a layer is only allowed to communicate with the layer right below it for the closed layer or any layers below it for the open layer. 
3.1.2 Impact on Architectural Characteristics
1. Performance:
Sequential processing across layers for peak load with 800 transactions for 30 minutes per factory is not massive but can accumulate latency. Every request must pass through each closed layer, including layers that add no logic for that request, so the fixed overhead per request is higher 
2. Availability:
Since edge devices are assumed to handle offline operations locally, central availability concerns shift to data synchronization. A network drop will halt real-time administrative workflows and delay historical data syncing, but local gates will remain.
3. Reliability:
        The synchronous top-down flow ensures an attendance record is saved under normal conditions. But a sudden network disconnection mid-flow can cause the transaction to fail, leading to lost attendance records.
4. Recoverability:
        Top-down logical architecture does not support offline sync mechanisms so external supporting patterns must be designed.
5. Scalability:
        Since all layers are bundled into a single application, specific functions cannot be scaled independently so to handle high QR scan traffic, the entire system must be scaled, wasting resources on unused features.
6. Maintainability:
        Layered Architecture creates clear boundaries by organizing code by technical function which allow to work simultaneously without interfering.
7. Extensibility:
        Simple configuration like adding new gates are easy but adding features often requires cross-layer modifications, increasing the risk of breaking existing code.
8. Security:
        Since all requests must pass through the top layers first, a centralized security filters can be set up to consistently enforce authentication and security rules before execute any business logic.
9. Privacy:
        Business layer ensuring the Presentation only receives necessary results without exposing raw personal data in the bottom layers.
10. Supportability:
        Requests move sequentially through the layers, error logs provide a clear, linear map of exactly where the process failed.
3.1.3 Strengths and Weaknesses for TMC System:
1. Strengths:
Layered Architecture is ideal for administration and reporting features by clearly separating the processing flow, especially for System with heavy CRUD use cases like TMC System (User and QR Code Management, Gate Station Management,..). With requests flowing sequentially through layers, TMC System can establish a security filter at the API or Business layer to ensure RBAC and record Audit logs before allowing the request to proceed. This facilitates Privacy and Audit requirements.


2. Weaknesses and trade offs:
Sinkhole Anti-pattern may occur for simple flows like recording an Audit log, a request might pass through multiple layers without any significant logic processing at the Business layer, creating structural redundancy. Changing a requirement requires modifications across all layers, which negatively impacts Extensibility. Besides, layered request flow is sequential which can create latency coupling, threatening NFR-01.
3.1.4 Critical Scenario Analysis:
1. Employee Access:
* Scenario flow: Employee scans QR -> QR Scanner/Gate Station (Presentation) -> Access validation (Business) -> Call Turnstile API (Integration) -> Record transaction (Data Access).
* Performance (NFR-01): This flow relies on synchronous processing speed. If the Integration layer waits for a slow Turnstile API response, or the Data layer writes to the DB slowly, the entire top-down flow is blocked and may violate NFR-01.
* Availability (NFR-06): NFR-06 requires the gates to keep operating when the connection to the central system is lost. A Layered Architecture requires a strict, continuous flow from the Presentation layer down to the Data layer. Since offline operation is handled locally by the gate, the Layered central system must process synchronized offline records once the network restores.
2. Attendance Synchronization to HR/Payroll:
* Scenario flow: Scheduled Trigger -> Aggregate Attendance data (Business) -> Format data (Integration) -> Call HR/Payroll System API.
* Maintainability: The Business layer encapsulates the aggregation logic, while the Integration layer isolates the external API communication. If the HR system's API specifications change, modifications are contained within the Integration layer. 
* Reliability & Recovery (NFR-05): NFR-05 requires guaranteed attendance data delivery to the HR/Payroll system by 12:00 PM. Layered Architecture executes flows in a synchronous, request-response manner. If the external HR API is temporarily unavailable the synchronous flow throws an exception and terminates. To achieve the automated retry and fault-tolerance required by NFR-05, the system is forced to introduce external components such as message queues or background workers that operate asynchronously outside the standard top-down layered flow.


3.2 Modular Monolith
3.2.1 Core concept
Modular Monolith is an architecture style where the entire system is built and deployed as a single application unit, but divided into independent, domain-driven modules. Each module encapsulates its business logic and data state. Modular Monolith communicates via in-memory function calls or internal events, while maintaining strict clear interfaces to prevent structural coupling.


3.2.2 Impact on Architectural Characteristics
1. Performance:
In-process communication between modules eliminates internal network latency overhead. This optimizes processing speed, making it capable of handling the peak load of 800 transactions within 30 minutes per factory.
2. Availability:
Although modularity isolates faults, the architecture is still deployed as a single process. A fatal runtime error acts as a Single Point of Failure that brings down the entire application.
3. Reliability:
Since all modules run in the same process and share a single database, traditional ACID transactions can be leveraged across modules. This ensures data integrity and no attendance records are lost.
4. Recoverability:
Modular Monolith does not natively support edge-device offline buffering or distributed synchronization.
5. Scalability:
Can be scaled horizontally by replicating the monolith across multiple servers. However, specific modules cannot be scaled independently leading to low elasticity.
6. Maintainability:
Domain boundaries make the codebase much easier to navigate and maintain compared to a traditional Layered architecture. Changes are isolated within specific modules, preventing the chain effect across the system.
7. Extensibility:
Adding new business capabilities involves creating a new module with its own API contract, causing minimal effects to existing core functions.
8. Security:
Authentication and RBAC (Role-Based Access Control) can be uniformly enforced at the entry point before routing requests to specific domain modules.
9. Privacy:
Modules like Attendance or Reporting only interact using identifiers, minimizing the exposure of raw personal data.
10. Supportability:
Application logs are centralized by default but can be easily filtered by module namespaces, making debugging and auditing easier.


3.2.3 Strengths and Weaknesses for TMC System:
1. Strengths:
Modular Monolith offers high performance without distributed complexity. It can handle NFR-01 by avoiding network communication between internal services. Enforcing data consistency for NFR-02 is simplified using local database transactions. The domain separation supports extensibility, allowing to update HR export logic or admin reports without changing the code of the access flow.


2. Weaknesses and trade-offs:
Modifying a minor feature in the HR Integration module requires rebuilding and redeploying the entire system. This could cause outages at the factory gates. 


3.2.4 Critical Scenario Analysis:
1. Employee Access:
* Scenario flow: Employee scans QR -> Gate Station Software validates locally -> Calls Turnstile API -> Stores the event locally -> Synchronises to the Attendance Module.
* Performance (NFR-01): In-memory communication between the Access, Employee, and Attendance modules eliminates latency. The only external variable is the network call to the physical Turnstile API. 
* Availability (NFR-06) : Since edge gates handle offline scans, the central Modular Monolith must process delayed records upon restoration. Processing these synchronized offline records synchronously can cause database spikes.
2. Attendance Synchronization to HR/Payroll:
* Scenario flow: Scheduled Trigger -> HR Integration Module -> Queries Attendance Module (in-process) -> Formats data -> Calls HR/Payroll System API (External).
* Maintainability & Extensibility: If the external HR system changes its API payload specifications, modifications are strictly confined to the HR Integration Module. The Access Control and Attendance modules remain completely untouched.
* Reliability & Recovery (NFR-05): NFR-05 requires guaranteed data delivery by 12:00 PM. While domain isolation protects other modules from HR API timeouts, the Monolith's internal processing remains synchronous by default. 
3.3 Pipeline Architecture 
3.3.1 Core concept
Pipeline Architecture organizes data processing flows into a sequence of independent steps. The core components include Filters connected by Pipes . The defining characteristic of this style is its strict one-way data flow from a source to a sink. By breaking down massive processes into discrete operations, it allows architects to easily add, remove, or rearrange filters without impacting the internal logic of other components in the chain.


3.3.2 Impact on Architectural Characteristics
1. Performance:
Data must be serialized and deserialized every time it passes through a pipe to the next filter. This accumulated structural overhead significantly for NFR-01.
2. Availability:
The system's availability depends on the implementation of the pipes. If a single filter crashes in a synchronous, in-memory pipeline, the entire flow stops. 
3. Reliability:
A pipeline lacks support for global state or distributed transactions. If an error occurs late in the pipeline, it is difficult to roll back actions taken by previous filters, which can be hard for NFR-02.
4. Recoverability:
If pipes are in-memory, a system crash causes complete data loss of payloads in transit. If pipes utilize persistent brokers , recoverability becomes more strong, as unprocessed data waits in the pipe.
5. Scalability:
If the Validation filter is CPU-intensive during shift changes, multiple instances of that specific filter can be spun up to drain the pipe faster.
6. Maintainability:
Code logic is decoupled into single-responsibility filters, making the codebase modular and easy to test.
7. Extensibility:
New business rules can be injected into the pipeline without modifying existing filters.
8. Security:
The data payloads traveling across multiple discrete components increases the internal attack area.
9. Privacy:
Employee information must flow through the pipes. Ensuring all intermediate pipes and filters encrypt and safely handle this data can lead to operational overhead.
10. Supportability:
Filters are stateless and lack shared context, tracking a failed request that died at some filter requires complex distributed tracing.


3.3.3 Strengths and Weaknesses for TMC System:
1. Strengths:
Pipeline architecture is a perfect candidate for the HR/Payroll Sync flow. Its extensibility allows TMC to easily insert new Access Control rules in the future without risking regressions in existing code. 


2. Weaknesses and trade-offs:
Pipelines are designed for asynchronous, fire-and-forget unidirectional flows. However, Gate Station requires a synchronous, bidirectional response. Furthermore, if TMC needs to pass a new hardware attribute from the Gate down to the DB, the data contracts of all intermediate pipes and filters must be modified.


3.3.4 Critical Scenario Analysis:
1. Employee Access:
* Scenario flow: QR Scanner Source -> Pipe -> Validation Filter -> Pipe -> Turnstile Integration Filter -> Pipe -> Attendance DB Sink.
* Performance (NFR-01): The pipeline's structural requirement to serialize, transmit, and deserialize data between sequential filters accumulates latency. 
* Reliability (NFR-02): The pipeline style lacks native transaction boundaries (ACID). If the Turnstile Filter successfully opens the physical gate, but the pipe to the Attendance DB Filter drops due to an error, the flow is severed mid-way. The gate opens, but the record is lost, with no built-in rollback mechanism.


2. Attendance Synchronization to HR/Payroll:
* Scenario flow: Extraction Filter (Reads DB) -> Pipe -> Transformation Filter (Formats payload) -> Pipe -> Transmission Filter (Calls HR API).
* Maintainability & Extensibility: The domain data extraction, format transformation, and external API transmission are segregated. Adapting to future HR API schema changes only requires modifying the Filter.
* Reliability & Recovery (NFR-05): By utilizing persistent message queues as pipes, if the external HR API goes down, the Transmission Filter will fail, but the pre-formatted data remains safely buffered in the preceding pipe. Once the HR system recovers, the filter resumes processing from the pipe without needing to restart


3.4 Microkernel Architecture
3.4.1 Core concept
Microkernel Architecture is a fundamental division of the system into core system and plug-in modules. The core system contains only the logic required to keep the application running, along with a mechanism to orchestrate the plug-ins. The plug-in modules are standalone, independent components containing specialized business rules, logic, or integration adapters.


3.4.2 Impact on Architectural Characteristics
1. Performance:
Because the core and plug-in modules run in the same application process, the architecture avoids network latency overhead. 
2. Availability:
A critical failure in the Core itself acts as a Single Point of Failure (SPOF).
3. Reliability:
Ensuring transactional integrity (ACID) is feasible but depends heavily on the strictness of the core and plugin. If a plugin interacts with the database directly instead of yielding state back to the Core, maintaining data consistency becomes complex.
4. Recoverability:
Microkernel does not provide offline buffering or data recovery capabilities.
5. Scalability:
Scaling requires replicating the entire Core System and all its plugins.
6. Maintainability:
Code maintainability is high because custom validation rules and third-party API integrations are completely abstracted away from the Core processing flow.
7. Extensibility:
Adding support for new hardware involves writing a new plugin matching the Core's interface contract.
8. Security:
The Core can enforce Authentication and RBAC before push the payload to any business plug-in.
9. Privacy:
The Core can be designed to encrypt before passing the payload to external integration plugins, ensuring strict data privacy.
10. Supportability:
Debugging a failed request requires registry and contract logging to identify exactly which version of which plugin failed.


3.4.3 Strengths and Weaknesses for TMC System:
1. Strengths:
By isolating hardware integrations, Microkernel Architecture aligns with TMC CO-1. If the company replaces its HR software in the future, the developers can change the HR plugin without touching the core attendance tracking logic.


2. Weaknesses and trade-offs:
The Core and plug-ins must communicate via interface contracts. If the business evolves and requires a new data field , the Core's contract must be modified, which breaks all existing plugins and forces a massive refactoring. Additionally, it suffers from the same network dependency vulnerabilities as Layered Architecture when deployed centrally.


3.4.4 Critical Scenario Analysis:
1. Employee Access:
* Scenario flow: QR Scanner sends payload -> Core System -> Core Registry resolves validation plugin -> Core resolves turnstile plugin -> Core commits to Attendance DB.
* Performance (NFR-01): The local registry resolution and in-process execution are high performance. The only latency is the final call from the plugin to the physical Turnstile API. 
* Availability (NFR-06): Since edge operations continue, the central Core System must synchronize offline records when the network recovers. The Core must process these events without triggering real-time Turnstile plugins.. 
2. Attendance Synchronization to HR/Payroll:
* Scenario flow: Scheduled Trigger in Core -> Core aggregates monthly data -> Passes payload to HR plugin -> Plugin formats and executes HR/Payroll API call.
* Maintainability & Extensibility: The Core is completely oblivious to the HR system's API schema. The logic for transforming attendance data into HR-compliant formats is encapsulated inside the HR plugin.
* Reliability & Recovery (NFR-05): In this architecture, a plugin is a stateless worker. If the HR API times out, the HR plugin fails and throws an exception back to the Core System. 


3.5 Service-Based Architecture
3.5.1 Core concept
Service-Based Architecture is a distributed architectural style that partitions a system into a small number of services grouped by business domain. The difference from Microservices is that these domain services share a single, centralized monolithic database. Services communicate with UI or external integrations via network protocols, via REST APIs or message brokers, combining the deployment flexibility of distributed systems with the data simplicity of monolith.


3.5.2 Impact on Architectural Characteristics
1. Performance:
Compared to a monolith, this distributed setup requires more network hops but the macro distributed nature avoids the massive internal network connection seen in microservices. However, shared schemas in database can lead to latency bottlenecks, affecting the NFR-01.
2. Availability:
Macro distributed modularity ensures runtime fault isolation. A crash or memory leak in another service will not bring down the Access Control Service. However, the shared database is still a Single Point of Failure (SPOF) for the entire system.
3. Reliability:
By relying on a shared database, the system easily utilizes ACID transactions across different business domains. This guarantees data integrity and ensures no attendance records are lost for NFR-02.
4. Recoverability:
As a server-side distributed architecture, it lacks mechanisms for edge-device data buffering or synchronization.
5. Scalability:
Unlike monolithic, this architecture allows independent, elastic scaling of specific services. The Access Control Service can be scaled horizontally to handle shift-change loads without allocating unnecessary compute resources to the other modules.
6. Maintainability:
The codebase is divided into logical and physical domains, making it easier to navigate, test, and deploy compared to a Monolith.
7. Extensibility:
Adding new services is straightforward. However, the shared database can be high coupling, modifying a core schema often requires coordinated, simultaneous deployments of multiple services to avoid breaking data contracts.
8. Security:
Each service can enforce its own security and RBAC.
9. Privacy:
Personal Information is managed within the shared database, allowing for uniform encryption and access must be audited.
10. Supportability:
Tracing requests requires centralized log across the distributed services.


3.5.3 Strengths and Weaknesses for TMC System:
1. Strengths:
Service-Based Architecture perfectly balances distributed scalability with complexity. Because TMC's peak load with 800 access transactions / 30 mins / factory is concentrated in the QR scanning flow, this architecture style allows elastic scaling of the Access Control Service during shift changes. The shared database solves the data integrity requirement NFR-02 by utilizing ACID transactions, avoiding the complexity of distributed data management. 
2. Weaknesses and trade-offs:
Because all services hit a single DB, a heavy administrative report query executed could lock tables or exhaust database I/O. This affects the Kiosk response SLA NFR-01 for the Access Service trying to write attendance logs. Furthermore, the architecture suffers from data coupling where changes to the shared schema require coordinated deployments across teams.


3.5.4 Critical Scenario Analysis:
1. Employee Access:
* Scenario flow: QR Scanner sends payload -> Access Control Service -> Queries Shared DB for validation -> Calls Turnstile API (External) -> Commits to Shared DB.
* Performance (NFR-01): Unlike a monolithic application, this distributed flow has multiple network hops from the edge Kiosk to the Access Service, down to the Shared Database, and outward to the physical Turnstile API. During the peak load, any degradation in the shared database's I/O performance will accumulate latency across these hops.
* Availability (NFR-06): Because local gates handle offline validation, the Access Control Service must synchronize offline records once the connection restores. This requires the service to distinguish between live requests and historical syncs without overwhelming the Shared Database. 


2. Attendance Synchronization to HR/Payroll:
* Scenario flow: Scheduled Trigger -> Administration & HR Service -> Queries Shared DB -> Aggregates & Formats -> Calls HR/Payroll System API (External).
* Decoupling & Isolation: The resources and processing threads required to extract, format, and transmit large batches of monthly attendance data are strictly isolated within the Administration & HR Service.
* Reliability & Recovery (NFR-05): If the external HR API times out or returns an error, the failure is fully contained within the Administration Service. 


3.6 Event-Driven Architecture
3.6.1 Core concept
Event-Driven Architecture is a distributed, asynchronous architectural style where independent software components communicate by producing, detecting, and consuming events. The system relies on event producers, event brokers and event consumers. Event-Driven Architecture is extreme decoupling via the fire-and-forget paradigm, a producer publishes an event without any knowledge of who will process it, when it will be processed or what the outcome will be.


3.6.2 Impact on Architectural Characteristics
1. Performance:
Event-Driven Architecture provides throughput for handling massive loads by absorbing requests into message queues. However, single-request latency degrades compared to monolithic styles due to the structural overhead of network hops and broker processing.
2. Availability:
Decoupling creates fault tolerance. If the consumer crashes, it does not bring down other consumers or the event broker, allowing the system to remain available for core operations.
3. Reliability:
The durability of event brokers ensures that messages are persistently stored. This guarantees that no attendance events are lost for NFR-02 even if databases are temporarily down.
4. Recoverability:
The architecture is designed to handle disconnected states. If a consumer disconnects, events queue safely in the broker and automatically synchronize once connection is restored.
5. Scalability:
 Consumers can be scaled elastically and independently. During shift changes, the system can scale up to drain backlog queues rapidly.
6. Maintainability:
While individual consumer codebases are small, single-purpose, and easy to test, the overall system behavior (often utilizing Event Choreography) becomes highly fragmented and conceptually difficult to trace.
7. Extensibility:
New business capabilities can be added transparently without modifying a single line of the core flow codebase.
8. Security:
Requires stringent security configurations at the Event Broker level, including strict Authentication/Authorization (ACLs) dictating which services are allowed to publish or subscribe to specific topics.
9. Privacy:
Personal Information flowing through event payloads must be encrypted both in transit and at rest within the broker to prevent unauthorized consumers reading the data.
10. Supportability:
Since the logical flow is asynchronous and distributed, mandatory implementation of tracing is required to debug exactly.


3.6.3 Strengths and Weaknesses for TMC System:
1. Strengths:
Event-Driven Architecture offers unparalleled support for system resilience and data integrity in NFR-02. Its inherent buffer capabilities make it resistant to traffic spikes. The architecture's retry mechanisms can reduce the need to write custom fault-tolerance logic. 
2. Weaknesses and trade-offs:
Event-Driven Architecture is asynchronous, forcing a synchronous response out of an asynchronous architecture requires implementing a complex messaging pattern where the Kiosk publishes an event, blocks its thread, and waits for a specific reply event. Furthermore, the system must accept administrative reports that might slightly slow behind real-time gate events.


3.6.4 Critical Scenario Analysis:
1. Employee Access:
* Scenario flow: QR Scanner publishes access request event -> Broker -> validation consumer processes and publishes passed event -> Broker -> turnstile consumer calls API and publishes open event -> Broker -> consumer logs to DB.
* Performance (NFR-01): Routing messages back and forth through the broker across multiple consumers accumulates network latency. 
* Availability and Recoverability (NFR-06, NFR-07): Event-Driven Architecture properties provide a solution when deployed topologically at the edge. By placing a local  broker directly at the factories, a disconnection may cause the edge Kiosk to publish events to the local broker. The local validation consumer processes the event and opens the gate offline. Since offline operations are managed locally, the central broker queues the burst of offline events synchronized from the gate stations, preventing the central consumers from being overloaded during network recovery.


2. Attendance Synchronization to HR/Payroll:
* Scenario flow: scheduler publishes sync event -> Broker -> HR consumer aggregates data and pushes to HR API.
* Failure Isolation & Recovery (NFR-05): If the HR API times out, the broker automatically pushes it to a Dead Letter Queue or retries cyclically, ensuring delivery before 12:00 PM without complex custom retry logic.

3.8 Architecture Selection
After a comprehensive evaluation, a Modular Monolith architecture is selected for the central system, complemented by edge processing at the gate stations.
While a Service-Based Architecture offers better scalability, TMC’s peak load does not justify the operational overhead of a distributed system. A Modular Monolith domain-driven structural clarity but utilizes in-process method calls instead of network hops. This eliminates internal network latency, ensuring the system consistently meets the strict 2-second kiosk response SLA. Additionally, enforcing strict data ownership within a shared database is significantly easier and safer within a single compiled codebase, preventing data coupling.

4.7. Key flows
Two flows show how the components work together.
Employee check-in or check-out
1. The employee presents a QR code at the QR scanner of a gate.
2. The QR Validator checks the signature, the expiry time, the employee status and the factory, using the reference data in the Local Store.
3. The QR Validator stores the access event in the Local Store, whether it is accepted or rejected, with the reason for a rejection.
4. If the code is valid, the Turnstile Adapter sends the unlock request to the Turnstile Control System, and the result is added to the stored event.
5. The Sync Client uploads the event when the connection is available. Event Intake stores it as an attendance transaction and ignores an event it has already received.
6. Event Intake publishes an audit event to the Audit Log.
Steps 1 to 4 need no connection to the central application, so the gate keeps working during a connection loss (NFR-06).
Monthly export to the HR/Payroll System
1. The Export Job starts according to the schedule held in System Configuration.
2. The Export Job reads the attendance data of the month through Attendance Query.
3. The HR/Payroll Adapter transmits the data through the HR/Payroll System API and returns the status, which the Export Job records.
4. If the transmission fails, the Export Job retries automatically. If the data is still not delivered, it notifies HR staff (FR-RA-05).
5. HR staff see the transmission and reconciliation status and can start a re-transmission.

5. Physical Architecture


TMC is deployed on one central data centre and two factory sites. The central data centre runs the Modular Monolith on two application servers behind a load balancer, with a primary and a standby database. At each factory, every gate has its own kiosk that validates QR codes, stores access events and unlocks the turnstile over the factory LAN. The kiosks synchronise with the central data centre over a VPN. This deployment is chosen for four reasons:


* Fast and independent gates. The path from scan to unlock stays inside the factory, so the response time does not depend on the WAN or on the load of the central system, and gates keep working when the central site is unreachable.
* No single point of failure. Every central node is duplicated, and every access event is stored at the gate before it is sent to the central database.
* Low operational cost. The load is modest, so a small number of nodes is sufficient. The design is simple to operate and can grow by adding servers or factory sites.
* Defence in depth. Firewalled zones, a VPN between sites and encryption on every link and data store protect personal data.

	6.2. Design Principles
Principle
	Guideline for TMC
	Single Responsibility
	Each module and class should have one reason to change. QR validation, turnstile communication and attendance recording are separate components, so a change in the Turnstile API does not touch attendance logic.
	Open/Closed
	New behaviour should be added by new code, not by editing existing code. A new access rule is a new class implementing the common validation interface; a new business capability is a new module.
	Liskov Substitution
	Any implementation of an interface should be usable wherever the interface is expected. A simulated turnstile adapter used for testing must behave like the real adapter from the caller's point of view.
	Interface Segregation
	Module interfaces should be small and specific to their client. The Reporting and Audit module uses a read-only attendance interface, and the gate station depends only on an unlock interface.
	Dependency Inversion
	Business logic should depend on abstractions that it defines, such as a turnstile gateway or a payroll exporter; the adapters implement these abstractions. Source code dependencies point inward, toward the business rules.
	Separation of concerns
	Business rules should remain independent of the user interface, the database and the external systems, so that each can change without affecting the others.
	High cohesion, low coupling
	Functions that change together should be placed in the same module, and modules should communicate through narrow interfaces instead of shared tables.
	Prefer asynchronous work outside the gate path
	Reports, exports, notifications and synchronisation should run in the background, so that only validation and unlocking sit on the 2-second path.
	Prefer configuration to code change
	Where a value may differ between factories or over time, it should be configurable.
	Design modules for later extraction
	A module should not rely on running in the same process as the others, so that it can become a separate service if new factories or requirements demand it (NFR-08).
	

M2 – Issues and Solutions
M2 raises two issues with the TMC system: connection loss during attendance transaction processing, and exposure of static QR codes.
1. Issue 1: Connection loss mid-transaction
Issue 1 concerns the attendance transaction itself, from the moment an employee presents a QR code until the event is safely stored in the central system. We analyse the four links on that path in two groups: the first three happen at the gate during the scan, within the 2-second budget; the fourth is the recording of the event in the central system. M1 handled only a full WAN outage, so M2 must also cover breaks in the middle of a transaction.
Link
	What happens if it breaks mid-transaction
	Proposed handling
	Phone ↔ server
	QR Display runs on the server, so an employee whose phone has no signal at the gate has no code. This is the largest gap.
	Generate the QR on the phone (see Section 2).
	Kiosk ↔ Turnstile (LAN)
	The unlock request is sent but times out; it is unknown whether the gate opened.
	Record the event as UNLOCK_UNKNOWN. Retry with an idempotency key or query the turnstile status. Notify the security guard.
	Kiosk power loss or crash
	An event is half written.
	SQLite WAL with fsync (AD-06 already requires a local write first). On restart, reconcile pending events.
	Kiosk ↔ data centre (during sync)
	Only part of a batch is uploaded.
	Outbox pattern with a per-event acknowledgement. Mark an event as synced only after the central commit. Extends AD-07.
	Extended offline operation. When the kiosk ↔ data centre link stays down for a long time, the gate keeps admitting employees but needs explicit rules:
* Clock drift: the NTP server sits in the data centre behind the VPN, so a WAN outage also removes the kiosk's time source and QR expiry checks become unreliable. Add a backup time source at each factory and allow a small tolerance.
* Stale revocations and keys: a gate only knows data up to its last sync. State this as an accepted trade-off.
* Maximum offline duration (configurable) and Local Store capacity, with an alert when a threshold is reached.
* Gate Monitoring alerts guards and administrators when a gate has been offline longer than a set period.
Turnstile failure (fail-secure). The Turnstile Control System is an existing external system: TMC only calls its API and never modifies it (CO-1). If the turnstile does not respond, TMC does not open the gate by itself; it records the event as UNLOCK_UNKNOWN and alerts the security guard. The guard lets employees through manually and records a manual entry with a mandatory reason (FR-AT-05), so no attendance record is lost. We call this behaviour fail-secure and state it explicitly; M1 (Table 5.6) already implies it. Emergency evacuation is handled by the turnstile hardware and the fire alarm system, outside the software scope.
2. Issue 2: Exposed QR codes
The main approach is a device-bound QR code: it is signed on the phone, valid for 15–30 seconds, and accepted only once. This blocks copying and replay, and it also removes the phone's dependency on the network from Issue 1.
How the device-bound QR works:
1. When an employee first signs in to the app, the phone generates a key pair. The private key stays in the phone's secure storage and never leaves the device.
2. The server issues a device certificate containing the employee ID, the device public key and an expiry (for example 7 days), signed by the server.
3. Every 15–30 seconds, the app signs (certificate + timestamp + nonce) to produce a new QR code. No network is needed.
4. The gate verifies the server signature on the certificate, then the device signature, the timestamp, the revocation list and the nonce. No network is needed either.
Both the phone and the gate therefore work offline, and a screenshot sent to another phone is useless once it is used or expires.
Limit to state clearly: if an employee hands their whole phone to someone else, the device-bound QR cannot detect it, because the code comes from the genuine device. Face capture at the kiosk could address this as a future extension, but it conflicts with the privacy requirement, so it stays out of scope.

	2. Key Connectors and Interactions
2.1. Primary Access Flow (Online or Offline)
1. The employee opens the Mobile App and generates a short-lived device-bound QR code (device certificate + timestamp + nonce, signed with the phone’s private key). No network connection is required. This is the M2 solution for static QR exposure and phone-side connectivity loss.
2. The employee presents the QR code to the QR Scanner.
3. The QR Scanner forwards the data to the QR Validator (local processing).
4. The QR Validator verifies the code using reference data held in the Local Store (signature, expiry, revocation list, factory authorisation).
5. The QR Validator writes the access event to the Local Store before any unlock attempt is made (AD-06).
6. If the code is valid, the Turnstile Adapter sends an unlock request to the Turnstile Control System over the factory LAN.
7. The result is written back into the local event record.
8. Later, the Sync Client uploads the event to Event Intake (via the API Entry Point) using the EventIntake interface. Event Intake performs an idempotent insert (AD-07).
Critical property: Steps 1–7 never require a connection to the central system. This directly solves Issue 1 (connection loss during transaction processing) and satisfies NFR-01 and NFR-06.
2.2. Synchronisation Connector
Sync Client - API Entry Point (HTTPS with mutual TLS over the site-to-site VPN)
• Upload: pending access events and gate status
• Download: reference data (employee status, verification keys, revocations, gate configuration)
The connector uses the EventIntake, ConfigReader and gate-status endpoints. An outbox pattern together with per-event acknowledgement guarantees that no event is lost and that no event is stored twice.
